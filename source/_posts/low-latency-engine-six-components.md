一笔订单从网卡进来，到变成交易所里的一条委托，中间至少要穿过六个部件：解码器、无锁队列、订单状态机、网关与预写日志、内存池、延迟统计。

每一件都能写一篇八股文。SPSC 要 cache line 对齐，WAL 要 CRC32 校验，状态机要幂等，内存池要避免 new。这些说法都对，但都对得没什么用——工程里真正难的问题不是「怎么实现」，而是**「它值多少纳秒，代价是什么」**。

所以这篇不做原理科普。我给这六个部件各写了一个微基准，在 M4 Pro 上各跑十轮取中位数，然后把数字摆出来。有几个结论和教科书一致，有两个正好相反。

先给全景，再逐个拆。

## 一、先立规矩

**环境**：

| 项 | 值 |
| --- | --- |
| 机器 | Apple M4 Pro（arm64） |
| 系统 | macOS 25.4.0 |
| 编译器 | AppleClang 21.0.0 |
| 构建 | Release + LTO（`live-benchmark-release` preset） |
| 被测模块 | `trading_engine`（C++20） |

**方法**：每个基准连续跑 10 轮，取中位数，同时记录最小值、最大值和变异系数（CV）。之所以不用平均值，是因为双线程测试里偶尔会有一次被系统调度打断的异常值，平均值会被它拖偏。

**为什么要看 CV**：单线程用例的 CV 普遍低于 2%，双线程用例在 4%–7%。**CV 本身就是信息**——它告诉你这个数字有多可信。文章里凡是 CV 超过 5% 的结论，我都会标注。

**必须先声明的四个局限**：

1. macOS 没有实时调度，双线程测试无法绑核，跨核通信成本受调度器影响；
2. 事件循环在 macOS 上走的是 `poll()` 后端，不是 epoll——所以本文不声称任何 epoll 数据；
3. 所有延迟是**应用层**测量（`steady_clock` 包住回调），不含内核协议栈时间；
4. 单个用例内部是单次采样，轮间取中位数，但没有做 CPU 频率锁定。

以上任何一条被忽略，后面的数字都会被误读。

## 二、第一件：无锁队列，3.6 纳秒和一次翻车

`SpscRingBuffer` 是一个单生产者单消费者环形队列。容量取 2 的幂，用 `& mask` 代替取模；`head_`、`tail_` 和两个缓存变量各自 `alignas(kCacheLineSize)` 独占一条 cache line。

先看单线程基线——push 和 pop 交替，容量压到 1024 让数据全留在 L1：

```text
spsc_single_thread    3.59 ns/op    (CV 24.4%，首轮异常，其余稳定在 3.57–3.60)
```

**3.6 纳秒**，约等于 280M 次操作/秒。这是原语本身的开销：一次 relaxed 加载、一次 release 存储，加上一次写数组。

然后是双线程，这是我最初以为会很精彩的部分。我写了两份实现：一份是生产代码里的 `SpscRingBuffer`（每个成员独立 cache line），一份是 `CompactRing`（逻辑完全相同，但四个成员紧挨着放，故意制造伪共享）。预期是前者大幅领先。

结果：

```text
spsc_padded_tight     28.84 ns/op    (CV 12.6%)
spsc_compact_tight    28.80 ns/op    (CV  6.4%)
```

**一模一样。**

我盯着这两个数字看了很久。加了 256 字节填充，一条 cache line 都没省下来？

### 为什么会这样

关键在于「谁在什么时候写哪条 cache line」。

逐条 push/pop 的模式下，生产者和消费者是**紧耦合**的：队列容量只有 1024，生产者填满就得等，消费者取空也得等。每一次 push 都必然伴随一次 head_ 的写入，每一次 pop 都必然伴随一次 tail_ 的写入，而消费者要判断「有没有数据」就必须读 head_。

也就是说，**每处理一条消息，head_ 和 tail_ 所在的 cache line 本来就必须在核间往返一次**。这是数据依赖决定的，不是伪共享造成的。padding 能消除的是「额外的」无效传输，消除不了「必要的」数据传递。

在这个场景里，必要传输的成本完全盖过了额外传输。

### 那么 padding 什么时候有用

把每次同步的粒度从 1 条改成 64 条（`push_bulk` / `pop_bulk`，每批只在批边界检查对端指针），再测一次：

```text
spsc_padded_batch64    22.35 ns/op    (CV 4.4%)
spsc_compact_batch64   29.97 ns/op    (CV 7.2%)
```

**差了 1.34 倍。**

批量之后，每 64 条消息才需要一次跨核同步。此时「必要的传输」被摊薄到 1/64，而伪共享带来的「额外传输」仍然是每批一次——于是 padding 的收益终于显现了。

这条曲线可以概括成一句话：

> **padding 的收益与同步频率成反比。逐条同步时它等于零，批量同步时它才开始兑现。**

这解释了一个常见的困惑：为什么有些项目加了 padding 却没变快，而另一些项目加了就快一倍。区别不在代码写得对不对，在**调用模式**。

顺带一说，这个实验还暴露了一个反直觉的现象：批量模式下 padded 版 22.35ns 反而比逐条模式下的 28.8ns **更快**。原因是批量把同步成本摊薄了，而逐条模式下每条都要付一次跨核往返。**减少同步次数比减少同步成本更有效。**

## 三、第二件：解码器，零分配值 5.5 倍

协议是定长二进制，`#pragma pack(1)`，大端序，价格用定点数（×10000）避免浮点上网络：

```cpp
struct MsgHeader {      // 16 字节
    uint8_t  type;
    uint8_t  _pad;
    uint16_t length;
    uint32_t seq_num;
    uint64_t timestamp;
};

struct QuoteMsg {       // 48 字节，正好塞进一条 cache line
    MsgHeader header;
    char      symbol[8];
    int64_t   bid_price;
    int64_t   ask_price;
    int32_t   bid_size;
    int32_t   ask_size;
};
```

解码器要处理三件事：粘包/半包（256KB 累积缓冲，按 `length` 字段切分）、乱序（64 槽重排窗口，按 `seq_num & 63` 直接定位）、畸形消息（计数并跳过）。

基准里同时编了一个 `legacy_decoder` 作为对照——它是典型的手写实现：每条消息 `new` 一个对象，用 vector 收集。

| 用例 | 新解码器 | legacy | 加速 | 新分配次数 | legacy 分配次数 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 连续 100 万条 | **6.24 ns** | 34.41 ns | **5.5×** | **0** | 1,000,002 |
| 半包 25 万条 | **30.55 ns** | 54.12 ns | 1.8× | **0** | 250,002 |
| 乱序 60 万条 | **16.71 ns** | 60.28 ns | **3.6×** | **0** | 800,001 |

三行数据的规模不同，但分配次数那一列是决定性的：**legacy 的分配次数永远等于消息数 + 2**，也就是每条消息一次堆分配。

5.5 倍的差距里，有多少来自设计、多少来自分配？看半包用例就知道了：半包把所有消息切成两段喂入，新解码器仍然零分配，但耗时从 6.24ns 涨到 30.55ns（**4.9 倍**）。

半包本身不分配任何东西。增加的成本全部来自「消息被切开」这件事：两次 `feed` 调用、一次边界检查、一次缓冲区状态更新。**这条 4.9 倍的曲线说明：分支和数据搬运比分配更贵。**

这个结论和很多人的直觉相反。大家默认 `new` 是低延迟的头号敌人，但在这台机器上，一次堆分配（在热路径、tcmalloc 已缓存的情形下）大约 20ns，而一次额外的分支 + memmove 可以是 24ns。

零分配依然是正确的目标——它把方差消掉了，而不只是把均值降下来。但它不是唯一的目标。

### 乱序那 16.71 纳秒花在哪

乱序用例每 3 条一组，按 `1 → 3 → 2` 的顺序喂入。第 3 条到达时发现 gap，先入 64 槽重排窗口；第 2 条到达后触发 `drain_reorder_buffer()`，连锁把第 2、3 条按序发出。

16.71ns 是**摊到每条消息**的成本。真正贵的是「发现 gap 的那一条」——它要走一次窗口插入 + 一次排水循环。但因为每 3 条里只有 2 条走这条路径，摊薄后看起来不吓人。

**这就是平均值类指标的危险之处**：它会把「少数很贵的路径」藏起来。真实行情里如果出现永久 gap，这一条的成本会更高。

## 四、第三件：状态机，14 个状态值 26 纳秒

订单状态机有 14 个状态、5 个终态。终态（FILLED / CANCELED / REJECTED / EXPIRED / DONE）一律拒绝任何出边，自转移直接返回 true 保证幂等。

成交回报要防重复：用一个 256 槽的环形数组记录最近见过的 `exec_id`，拒绝重复且非递增的累计成交量。

```text
state_machine_lifecycle   26.07 ns    完整生命周期（含 2KB 去重数组清零）
state_machine_illegal     24.50 ns    非法转移被拒绝的路径
```

这两个数字要小心解读：**26ns 里绝大部分不是状态机本身，而是 `OrderState` 构造时把 256 个 `int64` 清零**（2KB，约 20ns 量级）。真正的 `transition()` 只是一次白名单查表 + 一次枚举赋值，在个位数纳秒。

非法转移 24.50ns 比合法路径略快，因为它提前返回、没有走完整个生命周期。这也印证了「成本在构造不在转移」。

如果要在热路径上优化，方向不是把 `transition()` 写得更快，而是**别每条消息都构造一个新状态机**——用对象池复用，或者把去重窗口移到状态机外面按订单维度维护。这一点在第六节会看到回报。

## 五、第四件：WAL，持久化的价格是 29 微秒

`OrderGateway` 的预写日志是 48 字节定长记录，`#pragma pack(1)`，带 CRC32（IEEE 多项式 `0xEDB88320`，启动时惰性生成 256 项查表）。三种持久化档位：

- `ASYNC`：写入用户态缓冲，不主动落盘；
- `GROUP_COMMIT`：攒够 `wal_group_size`（默认 32）条才 flush 一次；
- `SYNC_EACH`：每条记录都 `fsync`。

同规模（2 万单）三档对比：

| 档位 | 吞吐 | 每单耗时 | 相对关闭 WAL |
| --- | ---: | ---: | ---: |
| 关闭 WAL | 3.53M/s | 283 ns | 1.0× |
| `ASYNC` | 3.80M/s | 263 ns | 0.93× |
| `GROUP_COMMIT` | 0.60M/s | 1,680 ns | **5.9×** |
| `SYNC_EACH` | 0.03M/s | **29,416 ns** | **104×** |

这张表是整个引擎里最贵的一页。

**每单 fsync 的边际成本约 29 微秒**——扣掉 283ns 的基线，是 29.1µs。这个数字比整条撮合路径（250ns）慢了 **116 倍**。

`ASYNC` 和关闭 WAL 几乎没差别（263 vs 283ns，差异在噪声范围内），因为它只是往用户态缓冲写 48 字节 + 算一次 CRC32。**这就是「不做持久化」的真实价格：几乎为零。**

`GROUP_COMMIT` 每 32 单 flush 一次，把 29µs 摊到 32 单上，理论值应该是 ~0.9µs/单，实测 1.68µs——多出来的部分是攒批、组提交和等 flush 完成的同步开销。

这组数据解释了一个设计选择：**为什么真实交易系统很少对每一单 fsync。** 29µs 意味着单线程每秒最多 3.4 万单，而市场行情峰值可能每秒几十万条。所以生产系统通常让 WAL 走 `ASYNC` 或组提交，把「权威状态」交给交易所回报——日志只用于崩溃后重建意图，不用于保证每一单都已落地。

如果业务真的要求「报单前必须持久化」，那 29µs 就是硬下限，只能靠多线程/多磁盘并行绕开，而不是靠优化代码。

### 崩溃恢复

`wal_recovery` 用例写 2 万单后重建网关，按 `INTENT_NEW` / `INTENT_CANCEL` / `REPORT` 三类事件回放：

```text
wal_recovery   2.02M 单/秒   495 ns/单
```

恢复速度比写入慢（495 vs 313ns），因为回放要重建订单对象、校验 CRC、跳过尾部损坏记录。但 200 万单/秒意味着即使积压了一天的日志，也能在秒级恢复。

## 六、第五件：对象池，5.8 倍

`ObjectPool` 预分配一块连续内存，空闲块用指针链表串起来，`allocate` / `deallocate` 都是 O(1)，池空返回 `nullptr` 而不是回退到 `new`（保持行为可预测）。

对照实验的模式是「稳态复用」：先取满 1024 个槽，然后循环「释放一个、申请一个」，模拟订单对象的生命周期。

```text
object_pool_reuse    4.24 ns/op    (CV 0.7%)
heap_new_delete     24.42 ns/op    (CV 0.3%)
```

**5.8 倍**，而且 CV 都低于 1%——这是全文最稳的一组数据。

要注意的是 `heap_new_delete` 的 24.42ns **已经是很乐观的情况**：glibc/libc++ 的分配器有 per-thread cache，同尺寸反复申请释放基本命中缓存。真实的订单对象大小不一、生命周期交错，分配器的表现会更差，碎片也会累积。

这也解释了第四节那个 26ns 的状态机成本：如果把 `OrderState` 放进对象池，那 20ns 的清零开销可以被复用时的「只重置用到的字段」替代，整体能降一大截。

**对象池的真正价值不是均值，是方差。** 4.24ns 的 0.7% CV 意味着延迟可预测；`new` 的 24.42ns 在压力下会长出长尾（内存整理、页缺失）。

## 七、第六件：延迟直方图，3.44 纳秒买来 86.6% 的误差

延迟统计用 64 个桶的对数直方图，桶号 = `std::bit_width(value)`，`O(1)` 写入、`O(1)` 内存，覆盖 0 到 2^63 纳秒全量程。

```text
histogram_record    3.44 ns/op    (CV 0.8%)   → 约 290M 次记录/秒
```

记录成本几乎可以忽略。代价在精度上。

我喂了 100 万个对数正态分布的样本（中位数约 1097ns，σ=1.2，模拟典型撮合延迟），然后对比直方图估计的分位数和排序后的精确分位数：

| 分位数 | 误差 |
| --- | ---: |
| p50 | 小 |
| p90 | 小 |
| p99 | 中等 |
| **p999** | **+86.6%** |

（误差定义为 `|估计值 − 精确值| / 精确值`，十轮结果完全一致，因为输入是固定种子。）

86.6% 不是 bug，是设计使然。`bit_width` 分桶的宽度是指数增长的：桶 `k` 覆盖 `[2^(k-1), 2^k - 1]`，而 `percentile()` 返回桶上界 `(1 << k) - 1`。所以**估计值永远偏大，最坏情况接近 2 倍**。p999 落在长尾区，那里桶很宽，误差自然最大。

这个取舍对不对？取决于用途：

- **做监控告警**：完全够用。你要的是「p999 是不是从 1µs 涨到了 10µs」，86% 的相对误差不影响这个判断。
- **写 SLO 报告、对比两个版本**：不够。两个版本的真实 p999 差 50%，直方图可能告诉你不存在差异。

**如果必须精确，就不要用直方图**；如果要 O(1) 内存和恒定写入成本，就接受这个误差，并且**在文档里写清楚误差上界**。最糟的做法是用它算出来的数字对外声称「p999 是 X」。

顺带说一句：这个直方图对本项目更重要的一点是——它让延迟统计本身的成本降到了 3.44ns，可以在热路径上无条件开启。**可观测性如果不能常开，就等于没有。**

## 八、缺席的那一件：事件循环

原本计划把事件循环也纳入基准，但没做成，原因值得写下来。

`NativeEventLoop::add()` 只接受 `TcpSocket&`，而 `TcpSocket` 是客户端封装，只有 `connect()`，没有「从裸 fd 构造」的入口。这意味着基准里没法用 `socketpair` 造一对本地 fd 注册进去。

我试的第一版是直接调 `wait(events, 0)` 空转，测出 2.66ns，看起来漂亮得可疑。查源码才发现 macOS 后端有这么一行：

```cpp
const size_t limit = std::min(events.size(), impl_->registrations.size());
if (limit == 0) return 0;     // 没注册任何 fd，直接返回
```

**没注册 fd，`poll()` 根本没被调用。** 那个 2.66ns 测的是函数返回，不是系统调用。

这是本文最有价值的一次翻车：它提醒我，**在相信任何微基准之前，先确认它真的执行了你以为它执行的代码。** 一个 2.66ns 的「系统调用」应该立刻触发怀疑，而不是被当成好消息。

所以事件循环的成本，本文只能由端到端数据间接覆盖，不给独立数字。要补这一块，需要先给 `TcpSocket` 加一个从裸 fd 构造的入口——这是接口设计问题，不是测量问题。

## 九、串起来：端到端 1.57M 事件/秒

单件测完，再看拼起来的表现。管线基准模拟完整链路：字节流 → 解码 → 每笔行情触发一次下单 → 网关发送 → 模拟成交回报。

| 用例 | 吞吐 | 每事件 | p50 | p99 | p999 | 最大停顿（中位） |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 行情突发 | 1.57M/s | 639 ns | 250 ns | 1.79 µs | 11.1 µs | **6.82 ms** |
| 半包 | 1.35M/s | 742 ns | 375 ns | 10.2 µs | 11.5 µs | 5.64 ms |
| 发送背压 | 1.52M/s | 657 ns | 334 ns | 2.25 µs | 5.8 µs | 5.61 ms |

先看一个容易误读的地方：**p50 是 250ns，但每事件是 639ns。** 不矛盾——p50 只测「回调内部」这一段（构造订单、发送、回报），而 639ns 包含解码器 `feed()` 的全部开销。两个数字量的不是同一件事。

半包用例的 p99 冲到 10.2µs，是行情突发的 5.7 倍。这和第三节解码器的结论一致：**半包路径的代价不在平均，在尾部。** 每 2 次 `feed` 才凑出一条完整消息，边界检查的成本只在「刚好切开」的那些消息上爆发。

`send_backpressure` 模拟了对端每次只收 17 字节、每 11 次阻塞一次的场景。它的 p99（2.25µs）反而比半包低——因为背压是「可预测的慢」，而半包是「无规律的额外分支」。

### 顺带得到的网关数据

| 用例 | 吞吐 | 每单 |
| --- | ---: | ---: |
| 5 万笔逆序成交回报 | 3.40M/s | 294 ns |
| 10 万单（关 WAL） | 3.18M/s | 315 ns |
| 10 万单（ASYNC WAL） | 3.19M/s | 313 ns |
| 2 万单 WAL 恢复 | 2.02M/s | 495 ns |

逆序回报 3.40M/s 说明 `process_report` 不依赖回报顺序——它按 `order_id` 查表，不维护全局序号游标。这是「券商回报乱序」这个真实场景下的必要条件。

而关 WAL 和开 ASYNC WAL 的差距是 **315 vs 313ns**，统计上没有区别。这再次确认：**ASYNC 档的 WAL 几乎是免费的，它的成本不在热路径上。**

## 十、尾延迟：p99 是 1.8 微秒，max 是 6.8 毫秒

上面那张表里有一列我没在正文强调：**最大停顿的中位数是 6.82 毫秒。**

对比一下：

```text
p50   250 ns
p99   1.79 µs
max   6.82 ms     ← 比 p99 大 3800 倍
```

六个部件的微基准都告诉我：最慢的一件是 29µs 的 fsync，而在关掉 WAL 的行情路径上，所有原语加起来不到 1µs。那么这个 6.8ms 是谁贡献的？

**不是引擎，是操作系统。**

6.8ms 是 macOS 时间片的量级。主线程在跑基准循环，一旦被调度器切走（后台索引、其他进程、电源管理），某一次回调的耗时就变成了整段时间片的长度。十个部件怎么优化都改变不了这个事实。

这条鸿沟是低延迟工程里最容易被忽略的：

> **应用层优化能决定 p50 和 p99，决定不了 max。max 由调度器和内核决定。**

这也是为什么真实低延迟系统要做那些看起来和代码无关的事——绑核（`pthread_setaffinity_np`）、实时调度（`SCHED_FIFO`）、隔离 CPU（`isolcpus`）、关闭中断合并、禁用电源管理。本项目里也有 `pin_current_thread()` 和 `set_current_thread_realtime()`，但**在 macOS 上两者都不可用**，所以这篇文章里没有它们的实测数据。

在 macOS 上你能做的是：承认 max 不可控，用它来衡量「环境有多吵」，而不是衡量「代码有多好」。

## 十一、一份代价清单

把六个部件的数字收拢成一张表。这张表是本文唯一的「结论」：

| 部件 | 单次成本 | 相对基线 | 代价 / 备注 |
| --- | ---: | ---: | --- |
| SPSC 单线程 | **3.59 ns** | 1× | 无竞争下的原语成本 |
| SPSC 跨核（逐条） | 28.84 ns | 8× | 跨核 cache line 往返，padding 无收益 |
| SPSC 跨核（批量 64） | 22.35 ns | 6.2× | 同步次数摊薄，padding 生效 1.34× |
| 解码（连续） | **6.24 ns** | 1.7× | 零分配；legacy 为 34.41 ns |
| 解码（半包） | 30.55 ns | 8.5× | 分支 + 缓冲区状态更新 |
| 解码（乱序） | 16.71 ns | 4.7× | 摊薄值；gap 那条更贵 |
| 状态机（含构造） | 26.07 ns | — | 主要成本是 2KB 清零 |
| 对象池分配 | **4.24 ns** | 1.2× | CV 0.7% |
| `new`/`delete` | 24.42 ns | 6.8× | 已命中的分配器缓存 |
| 延迟记录 | **3.44 ns** | 1× | p999 高估 86.6% |
| WAL 写入（ASYNC） | 263 ns | 73× | 相对 SPSC 基线 |
| WAL 写入（组提交） | 1,680 ns | 468× | 每 32 单一次 flush |
| **WAL 写入（每单 fsync）** | **29,416 ns** | **8,193×** | **29µs，全表最贵** |

基线取「3.59ns 的单线程 SPSC」，只是为了给一个统一刻度，不代表它们真的会串行叠加。

从这张表里能读出四件事：

1. **同步频率比同步成本更重要。** SPSC 从 3.59 涨到 28.84，涨的 25ns 全是跨核通信；而把同步次数除以 64，成本立刻回落。**减少同步次数是第一优先级，优化同步实现是第二。**
2. **分配的成本被高估，分支的成本被低估。** `new` 是 24ns，但半包多出来的分支是 24ns——在大致同一个量级。零分配的价值在方差，不在均值。
3. **持久化是唯一真正昂贵的东西。** 除了 fsync，所有部件都在纳秒级；只有它跨进了微秒。**「要不要持久化」是架构决策，「怎么优化代码」是次要问题。**
4. **精度和成本可以交换，但要知道自己在换什么。** 直方图用 86.6% 的 p999 误差换来 3.44ns 的记录成本——对监控是笔好买卖，对 SLO 报告不是。

## 结语

写这篇文章的起因，是我发现项目里那六个「面试重点」组件——注释里都标着 talking point——从来没有被单独测过。它们都实现得对，测试也过，但「对」和「值多少」是两件事。

测完之后，我有两个预期被推翻了：

一是 **cache line padding 在逐条模式下完全无效**。我一直以为它是无条件的优化，实际上它的收益完全取决于调用模式。

二是 **事件循环那个 2.66ns 的「系统调用」根本不存在**。它测的是 `if (limit == 0) return 0;` 这一行的返回时间。

第二个教训比第一个更重要。微基准最大的风险不是测不准，是**测了不该测的东西还浑然不觉**。所以这篇文章里我给每个数字都标了 CV，给测不成的那一件单独写了一节，也把 6.8ms 的 max 摆在 1.8µs 的 p99 旁边——它们一起才能说明这台机器上到底发生了什么。
