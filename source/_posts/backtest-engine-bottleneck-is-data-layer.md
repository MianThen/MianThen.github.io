有个数字我记了很久：**135**。

它不是某个比赛的加速比，也不是我调参调出来的倍数。它是我在自己的量化回测系统里量出来的一道裂缝——C++ 引擎每秒能吞 700 万行行情，而它上游的数据层，每秒只能喂进来 5.1 万行。

换句话说，我花了大半年打磨的那台引擎，在真实链路上有 **98% 的时间在等饭吃**。

这篇文章不是"我优化了引擎，快了 N 倍"。恰恰相反，它记录的是我准备优化引擎、结果发现**根本不该先动引擎**的全过程。如果你正在做回测系统、数据管道，或者任何"上下游速度不匹配"的系统，这个故事大概率对你有用。

## 一、先把结论摊开

我不想把结论藏在三千字后面。整篇文章的核心就这几行：

| 结论 | 支撑证据 |
| --- | --- |
| 引擎本体性能优秀：综合吞吐约 **700 万行/秒**，逐截面延迟 p50 0.65ms，p95/p50 只有 1.5 倍 | 全湖 1,410 万行，引擎内部只花 2.0 秒（解码 1.10s + 撮合 0.91s） |
| **真正的瓶颈在数据层**：引擎能吃 700 万行/秒，实际只被喂 5.1 万行/秒，差 **135 倍** | 端到端 277 秒里，引擎只占 0.7% |
| 根因是文件太小太多：**69.9 万个**平均 **4.3KB** 的 Parquet 文件 | 每文件固定开销约 341µs，批 p50 只有 21 行 / 1.2KB |
| 最优先的优化是**压实文件**，不是改 C++ | 预估端到端提升 15–25 倍；引擎侧优化在压实前收益 < 1% |

最后一条是我最想讲的。因为它意味着：**在我把数据层修好之前，所有针对引擎的优化都是自娱自乐。**

## 二、被测的是什么

整条链路长这样：

```text
数据湖(Parquet) → DuckDB/Arrow 扫描 → PartitionAwareIterator(有序截面)
    → Arrow C Stream / pybind11 对象 API → cpp_engine(撮合/持仓/绩效) → Python 策略回调
```

`cpp_engine` 是我自己写的 C++20 回测核心，以 pybind11 扩展的形式被 Python 调用。核心部分约 3.6k 行：`engine.cpp`（主循环，1538 行）、`order_book.cpp`（撮合）、`position.cpp`（T+1 与公司行动）、`pnl_tracker.cpp`（绩效）、`arrow_bridge.cpp`（Arrow C Stream 桥接，327 行）。Release 构建的 `.so` 只有 1.3MB。

我把它的卖点写在了 README 里：事件驱动、截面原子处理、A 股撮合规则（T+1、涨跌停、整手、参与率限制）、零拷贝 Arrow 接入、确定性可复现。这些后来都被测了，也确实都站得住。

测试数据是这样的：

| 项 | 值 |
| --- | --- |
| 平台 | Apple Silicon（arm64），macOS 25.4.0 |
| 扩展 | `cpp_engine` 0.3.0，Release，`cpp_engine.cpython-39-darwin.so` 1.3MB |
| 数据湖 | 2.9GB，**698,654 个 Parquet 文件**，14,105,167 行，约 2,500+ 标的 |
| 数据形态 | 日线，时间戳为上海 15:00 收盘，2006-01-04 → 2026-07-22 |
| 交易日截面 | 4,991 个 |
| 截面宽度 | 全湖均值 ~2,826 只/截面；2024 年后窗口均值 ~3,879 只/截面 |

> 顺带说一句：benchmark 框架里管这个叫 "minute replay"，但湖里实际装的是日线。这不影响结论——引擎与数据频率无关，延迟按截面宽度线性伸缩，后面我会给出分钟线的外推。

## 三、怎么测的：三条路径互不信任

先说方法论，因为**单一来源的性能数字永远可疑**。

我用了三条互相独立的测量路径，任何一条给出反常结果，都要能被另外两条交叉验证。

**第一条：分阶段基准。** 项目自带的 `run_minute_replay`，全湖无过滤，依次测量存储裸读、Arrow 解码、Arrow 纯计算、C 流回放、事件回放、策略回测六个阶段，每阶段记录耗时、行/字节吞吐、RSS、批延迟分位数。

**第二条：自研细粒度探针。** 取 2024-01-01 → 2026-07-23 窗口（2.39M 行、617 个截面），跑三个变体：

- **A**：对象 API 逐截面 `process_market_data_batch`，不带策略，纯测摄入延迟；
- **B**：同一路径挂一个双均线策略回调，返回 `Order` 对象，测端到端；
- **C**：`process_arrow_stream` 一次灌入 + 零拷贝 `MarketBatchView` 回调，用相邻回调之间的间隙估计引擎的逐截面处理延迟。

**第三条：引擎内部计时。** `process_arrow_stream` 直接返回 `decode_seconds` 和 `execution_seconds`，用 C++ 的 `steady_clock` 在引擎内部计时。这一条最关键——它能把"引擎花了多久"和"等待上游花了多久"彻底分开。

必须先声明的局限（这也是原报告的原文声明，不是事后补的）：

- 每阶段单次运行，没做多轮方差统计；
- 缓存状态不可控，没有 cold/warm 分离，首轮含冷缓存效应；
- 策略用的是最朴素的双均线（短 10 / 长 30，100 股整手，万三佣金），它的作用是压测引擎路径，**不代表任何策略研究结论**。

之所以还是敢下结论，是因为两条独立路径测出的数据层供给速率高度一致：全湖 51,216 行/秒，2024+ 窗口 50,423 行/秒。差 1.5%。这个稳定性足以支撑归因。

## 四、277 秒的解剖

全湖 14.1M 行，六个阶段的结果：

| 阶段 | 耗时 | 吞吐 | 备注 |
| --- | ---: | ---: | --- |
| storage_io（存储裸读） | 118.7s | 17.9 MB/s | 698,654 个文件逐个打开，均值 ~170µs/文件 |
| arrow_decode（DuckDB 扫描） | 239.0s | 59,020 行/s | 700,094 个批，**批 p50 仅 21 行 / 1.2KB** |
| arrow_compute（Arrow 纯计算对照） | 1.09s | 420 万行/s | 热缓存下 `pc.sum` 采样 |
| **c_stream_replay（引擎，一次流调用）** | 277.2s | 50,879 行/s | **引擎内部：解码 1.10s + 执行 0.91s = 2.01s** |
| event_replay（逐截面调用 ×4,991） | 275.4s | 51,216 行/s | 引擎执行 1.05s |
| strategy_backtest（含 Python 回调） | 272.4s | 51,780 行/s | 引擎执行 5.43s（4,991 次回调，每次下 10 笔单） |

这张表最刺眼的是同一行里的两个数字：**277.2 秒的总时间，和 2.01 秒的引擎内部时间。**

277.2 秒里，`storage_io` 和 `arrow_decode` 就已经用掉了 118.7 + 239.0 = 357.7 秒（有重叠，因为流式读取是交替进行的）。引擎拿到的每一行数据，背后都有一个打开文件、读 footer、解析 row group 的固定成本在等着。

算一笔账：

```text
端到端 277.2s
引擎内部 2.01s  →  占比 0.725%
其余 275.2s    →  占比 99.275%
```

即使加上 Python 策略回调，引擎执行也才 5.43 秒。**98% 到 99% 的时间，引擎在空转等数据。**

三个回放变体的吞吐几乎完全一样（50,879 / 51,216 / 51,780 行/秒），这个"巧合"本身就是证据：当供给速度是瓶颈时，下游怎么改都无所谓。你换接口、换调用方式、加不加策略，数字都在 5 万行/秒附近纹丝不动。

**这就是供给受限系统的典型特征。**

## 五、把引擎单独拎出来

如果故事到这里结束，结论就是"引擎不行"。但第三条测量路径给了完全相反的画面。

2024–2026 窗口，617 个截面，平均 3,879 只/截面：

| 路径 | p50 | p95 | p99 | max | 折算吞吐 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 对象 API 逐截面摄入（无策略，含 pybind11 转换） | 0.65ms | 0.95ms | 1.32ms | 51.4ms（首调预热） | ~500 万行/s |
| 流式路径引擎逐截面处理（回调间间隙） | 0.92ms | 1.53ms | 1.37s\* | 1.50s\* | ~420 万行/s |
| 纯 Python 策略回调体 | 4.30ms | 4.87ms | 5.11ms | 6.28ms | — |
| 对象 API + 策略（单截面端到端） | 7.03ms | 10.33ms | 21.28ms | 138.9ms | — |

\* 这两个尖刺不是引擎的问题，后面单独说。

**p50 0.65 毫秒处理 3,879 只股票的完整截面**，包括撮合、成交、现金、持仓、逐日估值。p95 是 0.95ms，p95/p50 = 1.46——延迟分布非常紧，没有长尾。这说明主循环里没有隐藏的分配抖动或锁竞争。

引擎内部的吞吐可以再拆开看：

- **纯撮合（noop 全湖回放）**：执行 0.91s / 14.1M 行 ≈ **1,540 万行/秒**，折合每截面 183µs；
- **解码**：全湖 1.10s，约 780ns/行，占引擎内部总时间的 **55%**。

是的，解码比撮合还慢。Arrow C Stream 的桥接层是逐行 `decode_row`，每行构造一个 `MarketSnapshot`，symbol 每行做一次 `std::string` 分配，还有每行两次 `steady_clock::now()` 计时——这些固定开销叠起来，把解码推到了引擎内部成本的 55%。

但请注意这个"慢"的量级：780ns/行，仍然是每秒 128 万行。它只是相对撮合慢，绝对性能一点不差。

### 那个 1.37 秒的 p99 尖刺

表里流式路径的 p99 是 1.37 秒，比 p50 大了三个数量级。第一次看到这个数字时我以为引擎有严重的尾延迟问题。

查下来不是。这些尖刺出现在相邻两次策略回调之间的间隙里，而这个间隙**包含了 Arrow reader 去 DuckDB 取下一个窗口数据的等待时间**。数据层的小文件问题，即使在流式过程中，也会以"停顿"的形式漏进引擎的延迟统计里。

这其实是整篇文章的一个隐喻：**你以为在测引擎，其实一直在测数据层。**

## 六、341 微秒的暴政

现在来算数据层这笔账。

`arrow_decode` 阶段 239.0 秒处理 698,654 个文件，平均每个文件 **341 微秒**。而每个文件里平均只有 20.2 行数据，4.3KB。

拆开看这个 341µs 花在哪：打开文件、读 Parquet footer、解析 schema、定位 row group、初始化列读取器、然后读出 20 行。其中真正的数据读取可能只占个位数微秒，剩下的全是**固定开销**。

在批这个维度上，数字更直观：700,094 个批，批行数 p50 = **21 行**，批字节数 p50 = **1.2KB**。批延迟 p50 0.23ms、p95 0.48ms。也就是说，系统在不停地处理 1KB 级别的数据块，每块都要付一次完整的批处理成本。

存储侧同样糟糕：裸读 2.9GB 花了 118.7 秒，**17.9 MB/s**。这块 NVMe 的顺序读能力大概是这个数字的一百倍。

再加一个密度指标：

```text
磁盘占用 / 行数 = 2.9GB / 14,105,167 行 ≈ 206 B/行
理论最小     = timestamp(8) + symbol(~10) + OHLCV(5×8) ≈ 56 B/行
膨胀倍数     = 3.7×
```

多出来的 150 B/行，绝大部分是每文件的 footer、schema、列 chunk metadata。文件越小，这部分占比越高。报告里估算 footer 类开销占 25–35%——这个比例在 4KB 的文件里完全说得通。

于是因果链闭合了：

```text
分区粒度太细（每 symbol 每月一个文件）
  → 文件数 69.9 万
  → 每文件固定开销 341µs × 69.9 万 = 238 秒
  → 数据层供给速率被钉死在 5 万行/秒
  → 引擎 700 万行/秒的能力无法兑现
```

## 七、0.7% 的利用率意味着什么

我一直觉得，"引擎利用率"这个指标比任何绝对性能数字都更有诊断价值。

```text
利用率 = 引擎执行时间 / 端到端时间 = 2.01s / 277.2s = 0.7%
```

0.7% 意味着：即使我把引擎优化到**无穷快**，端到端最多也只能从 277 秒降到 275 秒，提升 0.7%。

这就是 Amdahl 定律最朴素的应用，但它经常被忽略——因为优化引擎是"有趣的工作"，而优化数据布局是"无聊的工作"。人会不自觉地选择有趣的那一边。

更值得警惕的是这个数字在容量规划上的后果。我在 README 里写过引擎的设计目标是 120 亿行。按当前的数据层速率算：

```text
120 亿行 / 51,000 行每秒 ≈ 235,294 秒 ≈ 65 小时
```

而纯引擎时间呢？

```text
120 亿行 / 1,540 万行每秒 ≈ 780 秒 ≈ 25 分钟（按撮合速率，不含解码）
```

**65 小时 vs 25 分钟。** 差了 156 倍。所谓"120 亿行设计容量"，在当前数据布局下是个纸面数字——不是因为引擎不行，而是因为数据层根本喂不动。

再往分钟线外推一次。全市场约 5,000 标的 × 240 根 bar/日 ≈ 1.2 亿行/日。按实测的单行成本（75–240ns/行，含解码与撮合）估算，引擎内部耗时在 8–17 秒量级。一天的数据，引擎十几秒跑完——这本来是个很漂亮的数字，前提是数据层能跟上。

## 八、修法：顺序比方法重要

报告里给了 P0 到 P3 的四级方案，但真正的洞察不在方案本身，而在**顺序**。

### P0：文件压实（收益最大，必须先做）

把 `(year, month, bucket)` 分区内的小文件合并成"每月每 bucket 一个文件"，目标 row group 8–64MB，zstd + symbol 字典编码。产物写入新的 catalog generation，原分区保留为历史版本（符合"修订新建版本、不覆盖主键"的原则）。

预期效果：

| 指标 | 现状 | 压实后（预估） |
| --- | ---: | ---: |
| 文件数 | 698,654 | ~16,000 |
| 批 p50 | 21 行 / 1.2KB | 数万行 / 数 MB |
| 存储裸读 2.9GB | 118.7s（17.9 MB/s） | 2–4s |
| 全湖扫描 | 239.0s（59k 行/s） | 6–15s |
| **全湖端到端回放** | **277s** | **~10–20s（15–25 倍）** |

文件数从 69.9 万降到 1.6 万，是 44 倍的下降。原来那 341µs 的固定开销被摊到几万行上，摊薄了三个数量级。

顺带还能做一件事：压实重写时按 `(timestamp, symbol)` 全序落盘，catalog 打上"预排序"标志，`PartitionAwareIterator` 就能跳过每窗口一次的 `table.take` 全排序。这是一次写入、长期受益的交易。

### P1：桥接层与回调接口

压实做完之后，引擎内部时间占比会从 0.7% 升到 15–20%，这时候 P1 才开始有意义。

- **P1-a 列式解码 + symbol 字典化**：symbol 列改用 `dictionary<int32, utf8>`，解码时一次建"字典索引 → SymbolId"映射，行内只做整数映射，消除逐行 `std::string` 构造；数值列按缓冲区指针批量遍历；去掉每行两次 `steady_clock::now()`，改成每批计时后按行均摊。预期解码从 1.10s 降到 0.2–0.4s。
- **P1-b 列式回调**：现在订单侧已经支持列式 dict 返回，但**输入侧没有列式（numpy）接口**，策略只能逐标的虚调用（约 3,900 次/截面 ≈ 4.3ms）。新增 `set_on_cross_section_arrays`，回调入参直接是零拷贝的 `py::array_t`，预期回调从 4.3ms 降到 0.1–0.3ms。

### P2/P3：并行、分发与语义

多进程参数扫描（每进程约 1GB 稳态 RSS）、发布 Release wheel 免去本地编译、暴露 `can_sell()` 之类的预检 API、提供拒单原因聚合。

`can_sell()` 这条后来被证明特别值钱——测试里 88,815 笔委托有 63,916 笔被拒，**72% 的拒单来自 T+1 可卖约束**。策略在疯狂下注定被拒的单，纯粹是在浪费撮合路径的 CPU。把这层判断前移到策略侧，比任何微优化都有效。

### 为什么顺序不能乱

```text
压实前：引擎占比 0.7%  → P1 对端到端的影响 < 1%
压实后：引擎占比 ~20%   → P1 才开始显性化
```

如果在 P0 之前做 P1，你会得到一份"解码快了 3 倍"的漂亮报告，然后端到端时间几乎不变。这种"局部正确、全局无效"的优化，是性能工作里最常见的陷阱。

## 九、顺手测出来的正确性

性能测试往往会顺带暴露正确性问题，这次也不例外。这部分不是本文重点，但值得记一笔，因为它说明"快"和"对"可以同时验证。

| 检查 | 结果 |
| --- | --- |
| 对象 API 路径 vs Arrow C 流路径（同策略同数据） | **权益逐位一致**：1,196,621.0555；成交 24,782 / 轮次 12,056 / 订单 88,815 完全相同 |
| A 股规则压力 | 88,815 笔委托：24,782 FILLED / **63,916 REJECTED** / 117 EXPIRED |
| 绩效量级 | 总收益 +19.66%、年化 7.28%、Sharpe 0.340、最大回撤 25.50%、轮次胜率 32.84% |
| 输入校验 | 乱序、跨批时间戳、空 symbol、重复 symbol 均被快速拒绝，异常后引擎进入防污染状态 |

两条完全不同的执行路径（对象数组逐截面 vs 一次 Arrow C Stream 灌入），跑出的小数点后四位都一样的权益。这比任何单元测试都更有说服力——它证明零拷贝路径没有偷偷改变语义。

内存方面也值得一提：

| 阶段 | RSS 起点→终点 | 进程峰值 |
| --- | --- | ---: |
| storage_io | 795MB → 47MB | 856MB |
| arrow_decode（DuckDB） | 48MB → 3,966MB | **4,133MB** |
| c_stream_replay | 1,369MB → 991MB | 4,629MB（沿用峰值） |

引擎本身的内存是**有界且与历史长度无关**的（流式、不落全量），稳态约 1GB。4.6GB 的峰值全部来自数据层的 DuckDB 解码阶段。这也从侧面印证了归因：吃内存的是数据层，不是引擎。

指标查询的增量维护做得也不错：权益曲线 617 个点 0.10ms，Sharpe 6.1µs，最大回撤 0.58µs。这些是 O(1) 维护的，不随历史长度增长。

## 十、五条可迁移的教训

抛开这个具体项目，我觉得有五条经验适用于任何"上下游串联"的系统。

**第一，先测利用率，再谈优化。** 引擎利用率 0.7% 这个数字，比任何 microbenchmark 都更早、更准地告诉我该干什么。在动任何一行代码之前，先算出"这段代码占总时间的百分之几"。如果不到 5%，它就不配进入优化清单。

**第二，永远在真实链路上测。** 如果我只跑引擎的单元基准，会得到"700 万行/秒，非常好"的结论，然后心满意足地收工。是端到端测量揭穿了真相。脱离链路的性能数字，只对链路本身有意义。

**第三，吞吐一致就是供给受限的信号。** 三个变体的吞吐都在 5 万行/秒附近（50,879 / 51,216 / 51,780），差异不到 2%。当你改了调用方式、加了策略、换了接口，数字却纹丝不动时，说明瓶颈根本不在你改的地方。

**第四，小文件是分布式系统的原罪。** 4.3KB 的文件不算"小"，但 69.9 万个 4.3KB 的文件就是灾难。任何按细粒度分区的存储方案，都要先算一笔账：`文件数 × 单文件固定开销`，这个乘积会悄悄吃掉你所有的性能预算。

**第五，局部最优会伪装成进展。** 解码占了引擎内部 55% 的成本，看起来是最该优化的点。但在压实之前优化它，端到端收益小于 1%。**"在正确的方向上做小事"远胜于"在错误的方向上做大事"。**

## 结语

这篇文章的原始报告，是 2026 年 9 月 11 日写的。当时我刚完成一轮全湖评测，本意是给引擎做一次性能基线，然后按 P1/P2 逐项优化。

结果基线告诉我：引擎不用优化，数据湖要重做。

这算不上一个令人愉快的发现——它意味着我接下来几个月的工作重心，从我熟悉的 C++ 主循环，转移到了 Parquet 分区策略、row group 大小、字典编码这些"脏活"上。但我觉得这恰恰是性能工作最有价值的部分：**它不负责让你写更漂亮的代码，它负责告诉你哪里才是真正的战场。**

如果你也在做类似的事，我的建议只有一句：先把 `引擎时间 / 端到端时间` 算出来。如果这个比值小于 10%，关掉 profiler，去检查你的数据布局。
