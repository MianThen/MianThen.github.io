上一篇里有一道裂缝：C++ 引擎每秒能吞 700 万行，数据层每秒只喂 5.1 万行，引擎有 98% 的时间在等饭。

这次把饭端上来了。端上来的方式是**一行引擎代码都不改**。

复现的核心数字：

| | 压实前 | 压实后 | 倍数 |
|---|---|---|---|
| 文件数 | 698,654 | 15,808 | **44.2x** |
| 总查询耗时 | 107.624s | 6.913s | **15.57x** |
| 逐行迭代耗时 | 66.035s | 4.498s | **14.68x** |
| 行吞吐 | 33,386 行/s | 490,145 行/s | **14.7x** |
| 峰值内存 | 1,592.8 MB | 574.4 MB | **2.8x** |

下面是被这个结果反复打脸之后，我认为真正值得记下来的部分。

## 一、病根不是字节数，是文件数

先看两个数：

- 数据湖总字节：**不到 3 GB**
- 数据湖文件数：**698,654**

平均每个文件 **4.3 KB**，装 **20.2 行**。按批看更清楚：`batch_rows_p50 = 21`，`batch_bytes_p50 = 1236` 字节。

一个 4 KB 的文件，从打开、读 footer、解析 row group 元数据、解压、到交出 20 行，全程固定的 I/O 与元数据开销大概 **0.52 毫秒**。数据本身只值几微秒。

69 万个文件 × 0.52ms ≈ 6 分钟。这就是那 277 秒里的绝大部分——**引擎内核实测只占 2.01 秒**。

所以问题从来不在压缩率，不在列存格式，也不在 Arrow 解析器。**问题在网络存储上放了 69 万个小文件。** 顺带一提，这块盘是 exFAT，小文件性能本来就差，把这件事又放大了一层。

## 二、方案：只动数据层

压实规则很简单：按 `year=YYYY/month=M/bucket=K` 重新分片。

`bucket` 是 `symbol` 的 CRC32 哈希取模（64 个桶），保证同一 symbol 永远落在同一分区。数据跨度 2006-01 到 2026-07，共 **247 个月 × 64 个桶 = 15,808 个文件**。

这个数没法再少了：再少就意味着单文件跨月，查询要读无用数据；再就意味着削弱分区裁剪。**15,808 本身就是这张表的最优解。**

压实后的目录：

```
data/lake_compact/bars_compact/year=2024/month=3/bucket=17/part-compact-0.parquet
```

单文件从 4.3 KB / 20 行，变成约 43 KB / 1,180 行（`batch_rows_p50 = 1188`，`batch_bytes_p50 = 69947`）。总字节几乎没矮——**672 MB**——但文件数少了 44 倍。

引擎一行没改，查询计划一行没改，只是彼端换了个根目录。

## 三、逐查询对比

同一批查询，两个湖各跑一遍，每次都比对返回行数：

| 查询 | 旧湖文件 | 新湖文件 | 旧湖迭代 | 新湖迭代 | 加速 |
|---|---|---|---|---|---|
| `2024_full` | 45,358 | 768 | 22.93s | 1.121s | **20.45x** |
| `2024_m01` | 3,759 | 64 | 5.239s | 0.670s | **7.82x** |
| `2024_m01_d02` | 3,751 | 64 | 5.217s | 0.626s | **8.33x** |
| `2022_full` | 43,591 | 768 | 22.031s | 1.128s | **19.53x** |
| `2006_full` | 16,238 | 768 | 10.618s | 0.953s | **11.14x** |

注意时间窗口较窄时加速比会掉下来（7~8x），因为固定开销里还有一部分是**不分区的初始化**，压不掉。这也解释了为什么总加速 15.57x 而单查询能到 20x。

还有一条没进表但更刺眼：**旧湖在这台 15 GB 的机器上根本跑不完一次全湖回放**。我用 `--target-mb 256` 跑，内存涨到 12.2 GB 被系统杀掉；降到 `--target-mb 32` 仍然在 5 分 43 秒撞到 10.8 GB。新湖全湖回放 **70 秒 / 峰值 863 MB**。

也就是说：压实不只是让旧路径变快，它把一条**原本不可执行**的路径变成了可执行。

## 四、验收：为什么"结果对得上"这句话不成立

真正耗时间的不是压实本身——压实全湖只花了几分钟。耗时间的是回答一个问题：**凭什么说两边的数据是一样的？**

这个问题之所以难，是因为压实有一类失败方式特别阴险：**静默丢行**。

举个具体的例子：如果压实顺手过滤了 `volume = 0` 的停牌行，或者整根 bar 全平的行——数据看起来完全正常，schema 没变，回测照样跑，权益曲线照样画出来，只是少了一部分行。你翻遍日志找不到任何错误。

所以我把验收拆成三组，每组都在防一种特定的"静默"。

### A 组：数据本体

| 检查 | 防的是什么 |
|---|---|
| `count(*)` 与 `count(DISTINCT (timestamp,symbol))` 分别对比 | 过滤掉重复行，或静默丢行；两者相等才说明主键完整性未被破坏 |
| 逐列值**位级**一致（`float64` 不能降成 `float32`） | 降精度后回测仍能跑，但权益会差在小数点后 |
| 双向 `EXCEPT ALL` 两个方向都必须为空 | **单向**差集抓不到"多出来的行" |
| 每个 symbol 的 `min/max` 时间戳与交易日集合 | 总行数对得上，但某个标的历史被截断——这种情况最难发现 |
| 每日截面宽度分布（p50/mean）与基线对比 | **漏掉一个 bucket = 静默缩小 universe 七到八成**，回测照样运行 |

结果：主键唯一性 14,105,167 两湖一致；跨 20 年抽 10 个月（2006-01、2008-03、2010-07、2012-11、2015-06、2018-09、2020-04、2022-01、2024-01、2026-07）双向差集全为 0；全列位级一致；逐 symbol 时间范围与交易日集合全过。

这里踩了个坑值得单独说：**第一次跑 B4 检查时报了 1/3000 失败**，我差点去查数据。实际是校验器写错了——那个旧湖文件有两个 row group，行按 symbol 交错而非全局有序，所以 `row_group[0].min` 不等于文件全局 `min`。改成对所有 row group 取 `min/max` 后 22/22 通过。压实后的文件是全局有序的，15,808 个全过。

**校验器出错的样子，和被测数据出错的样子，是一模一样的。** 这一条后面还会再咬我一次。

### B 组：catalog 元数据自洽性

| 检查 | 预期 |
|---|---|
| `schema_hash`（只含 schema 版本/列/主键/时间单位） | **必须不变** |
| `dataset_fingerprint`（含 catalog 代数 + 每文件 path/size/rows/content_hash） | **必须变** |

这两个必须一正一反。如果 `dataset_fingerprint` 没变，说明指纹没真正覆盖文件级信息；如果 `schema_hash` 变了，说明 schema 真被动了——那就不叫压实，叫数据迁移。

实际结果：`schema_hash` 相同，`dataset_fingerprint` 变化，catalog 代数 10 → 11，逐月 bucket 集合完全一致，备份 `catalog.json.bak.<gen>` 齐备。22/22 通过。

这条的连锁后果要提前想清楚：**所有基于 `dataset_fingerprint` 的旧缓存和审计记录会全部失效**，feature cache 需要重建。这是预期行为，不是故障。

### C 组：下游消费者回归

- `query` / `iter_batches` / `cross_section` / `history` / `list_symbols` 五个 API 的返回 schema、行数、排序、symbol 集合逐项对齐（15 项检查）
- 六个既有测试文件全绿：`test_market_data_lake`、`test_p2_data_path`、`test_data_feed`、`test_backtest_runner`、`test_persistence`、`test_backend_parity`，加重实模块测试共 **77 项**
- 写路径：压实后 ingest 一个新文件仍成功，`count(*)` 仍等于 `count(DISTINCT (timestamp,symbol))`（14,105,182），幂等重放返回 `skipped=True` 且不产生重复主键

## 五、验证器本身必须被验证

上面那些检查全部返回 PASS。但**PASS 本身不构成证据**——一个永远返回 PASS 的校验器，和没有校验器是一样的。

所以我给校验器做了负向对照，故意构造四种该失败的情况：

| 对照 | 构造的问题 | 期望 | 实际 |
|---|---|---|---|
| NC1 | `--limit 1` 只压实 1/192 个分区 | 退出码非零 + FAIL | 退出码 **1** + `等价性: FAIL` ✓ |
| NC2 | 完整压实 | 退出码 0 + PASS | 退出码 **0** + `等价性: PASS` ✓ |
| NC3 | 改掉某分区第 0 行 `close` +999 | `equal: False` | **False**，且定位到具体分区 ✓ |
| NC4 | 删掉一行 | `equal: False` | **False** ✓ |

另外测了可重复性：同一源压实两次，**192 个输出文件字节级完全相同**。输出确定性，不内嵌写入时间戳，不依赖执行顺序。

这一步比前面所有 PASS 加起来更重要。**只有先证明校验器会喊"错"，它的"对"才有意义。**

## 六、端到端：双均线逐位比对

前面验的是数据本体和接口契约。但真正要对齐的是**撮合、持仓、绩效三层**。

我写了一个确定性的 MA(10/30) 全市场双均线探针：逐 symbol 维护 10/30 周期收盘均线，上穿买入、下穿卖出，固定 1 手，手续费按成交额 0.0003，同一批 bar 内先统一算信号再统一下单，无随机、无时间依赖。两湖跑**同一个 run_spec**。

2024 年第一季度（218,078 行）：

| 指标 | 旧湖 | 压实湖 |
|---|---|---|
| 买/卖信号数 | 3,524 / 871 | 3,524 / 871 |
| **equity** | **1001578.8727000001** | **1001578.8727000001** |
| **total_return** | **0.0015788727000001224** | **0.0015788727000001224** |
| **trades / round_trips** | **4,032 / 520** | **4,032 / 520** |
| 耗时 | 90.32s | **3.44s（26.3x）** |

2024 全年（914,906 行）：

| 指标 | 旧湖 | 压实湖 |
|---|---|---|
| 买/卖信号数 | 16,198 / 15,491 | 16,198 / 15,491 |
| **equity** | **997535.138** | **997535.138** |
| **total_return** | **-0.0024648619999999566** | **-0.0024648619999999566** |
| **trades / round_trips** | **31,182 / 15,007** | **31,182 / 15,007** |
| 峰值 RSS | 2,107 MB | — |
| 耗时 | 164.44s | **8.46s（19.4x）** |

权益、收益率、成交笔数、完整轮次全部逐位相同。

但我觉得最有信息量的不是这些，而是：**信号数完全相同**。

诚信号意味着 MA 状态推进对**行顺序不敏感**。而压实干的正是全局重排序——原来的行按 symbol 交错，现在按时间戳全局有序。行顺序变了、信号数一个不差，说明压实没有在边界上切碎任何一根 bar，也没有让同 timestamp 的截面被拆到不同批次里。

这是我事前最担心被破坏的性质，因为它不会体现在行数上。

## 七、三个教训

**第一，"差不多了"是个陷阱。**

压实后我在旧湖上重跑全湖回放，跑到 10.8 GB 被杀掉。当时第一反应是"压缩没生效吧"，实际上压实后的湖只有 672 MB——旧湖本身根本装不进这台机器。如果我事先没有做全湖回放的基线，很可能把"目标达成"当成"新方案有问题"，然后回头去优化一个根本没问题的东西。

**第二，文档里的基准数字会烂掉。**

项目文档 §9 记着一组很漂亮的基线：`equity 1,196,621.0555`、成交 24,782、轮次 12,056、订单 88,815。我想拿它做端到端验收，结果发现这组数字出自一个**已经被删掉的探针脚本**，标的筛选、仓位分配、下单量、手续费全是空白。文档里给的重现命令实际跑的是另一个策略。

结论很直接：**一个无法复现的基准，不能当验收基准用。** 所以我改成自己写探针、给出完整可执行的重现命令。数字不如那组好看，但它能被人重跑。

**第三，最贵的检查是那个"看起来没必要"的检查。**

`EXCEPT ALL` 做两个方向、每个 symbol 单独比时间范围、每日截面宽度分布——这三项在结果全绿的时候都显得冗余。但它们防的恰好是三类只在特定条件下才现形的静默错误：多出来的行、被截断的标的、缩小的 universe。这些错误不会让程序崩溃，只会让回测结果悄悄偏移，而你可能三个月后才发现权益曲线不对。

最后一个想法。

这件事的荒谬之处在于：系统里最慢的那个部件，字节数其实最小。3 GB 数据、672 MB 压实后，却支配了 277 秒里的 275 秒。性能问题不一定长在"数据多"上，也可能长在"数据碎"上——而"碎"这个维度，监控面板通常不显示。

指标上我加了一条：`batch_rows_p50`。它从 21 变成 1188 的那天，才是这条链路真正修好的那天。
